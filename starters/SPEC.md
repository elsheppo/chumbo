# Chumbo starter kits

Status: First starter (`team-tasks`) implemented and verified\
Owner: Chumbo OSS\
Related: [`SPEC.md`](../SPEC.md), [`ROADMAP.md`](../ROADMAP.md)

## 1. Problem

Chumbo's promise begins with an existing Supabase application. `chumbo setup`
refuses to run without `supabase/config.toml`, and the generated `whoami` tool
is deliberately a diagnostic. That serves adopters who already have a schema,
users, and RLS policies, but leaves two groups without a path:

1. **Greenfield builders** who want to start an MCP-capable product on Supabase
   today. Their nearest alternatives scaffold an MCP Edge Function with no
   authentication and no database.
2. **Evaluators** who want to _see_ Chumbo's core claim before adopting it: two
   people connect the same MCP endpoint and each receives only the rows their
   RLS policies allow. Reproducing that today requires a schema, policies,
   fixture users, seed data, a consent page, and a client.

## 2. Outcome

A builder runs one command and receives a complete, runnable, full-stack
Supabase application whose MCP server is already built in:

```sh
npx chumbo create team-tasks my-app
cd my-app
supabase start
npm run dev
```

Within minutes they can sign in to the web app as one of two seeded users,
connect an MCP client to the local endpoint through the real OAuth flow and
consent page, and watch the client see exactly what that user sees in the app.

## 3. Shape of a starter kit

Every starter is one repository with three parts sharing one Supabase project:

```text
<starter>/
├── starter.json            # catalog manifest (id, title, auth mode, demo users)
├── README.md               # five-minute path, then "make it yours"
├── AGENTS.md               # instructions for coding agents extending the kit
├── package.json            # root scripts: dev, build, check, test
├── supabase/
│   ├── config.toml         # Auth + OAuth server enabled for local development
│   ├── migrations/         # application schema and RLS (application-owned)
│   ├── seed.sql            # two demo users with disjoint and shared data
│   └── functions/mcp/      # generated by `chumbo init`; capabilities.ts authored
└── web/                    # thin Vite + React + supabase-js frontend
```

### 3.1 Backend

- The schema, RLS policies, and seed are ordinary application code. They are an
  example application, not a Chumbo recommendation: Chumbo still does not
  choose an application schema or authorization model.
- `supabase/functions/mcp/` is produced by `chumbo init` with the starter's
  access mode. Only `capabilities.ts` is hand-written. A drift check
  regenerates the function from the current package and fails when the
  committed generated files differ, so starters always show the ordinary
  generated path and remain upgradeable with `chumbo setup --resume`.
- Capabilities query only through `ctx.supabase`. RLS, not handler code, is the
  authorization boundary.
- The seed contains at least two users whose data overlaps partially, so the
  isolation demonstration works immediately after `supabase start`.

### 3.2 Frontend

The frontend is deliberately thin. It is the part with the highest maintenance
cost (framework churn, UI dependencies), so it contains only:

1. email/password sign-in and sign-up;
2. one view and one mutation over the same data the MCP exposes;
3. the OAuth consent route at `/oauth/consent`, wired to Supabase Auth's
   OAuth 2.1 server (`getAuthorizationDetails`, `approveAuthorization`,
   `denyAuthorization`);
4. a "Connect an agent" panel that shows the MCP URL and copyable client
   commands.

Vite + React is the first frontend: the result is static, so the Edge Function
is unambiguously the MCP host, and the shape matches the Vite + React +
Supabase projects many builders already have. No router, state, or UI library
is added. A Next.js variant is a follow-on (§8).

### 3.3 Agent readiness

Each starter carries an `AGENTS.md` that names the files a coding agent should
change for common requests (add a tool, add a table, add a policy) and the
commands that prove the change. The Chumbo skill can be installed with
`npx chumbo skill install`; the starter does not vendor it so it stays
version-matched.

## 4. `chumbo create`

```text
chumbo create [starter] [directory] [--list] [--json] [--force]
```

- Starters ship inside the published `chumbo` package, so the kit always
  matches the CLI version that creates it. No network fetch is needed.
- `--list` (or no arguments in JSON mode) prints the catalog from each
  `starter.json`.
- `directory` defaults to the starter id. The target must be absent or empty
  unless `--force` is passed; `--force` never deletes existing files, and
  refuses to overwrite a file that already exists.
- The copied tree excludes `node_modules`, build output, `.env` files, and
  Supabase's local `.temp`/`.branches` state.
- `supabase/config.toml` `project_id` is rewritten to a slug of the target
  directory so several starters can coexist on one machine's Docker.
- The command prints the ordered next steps; `--json` emits a machine-readable
  receipt for agents.

## 5. The first starter: `team-tasks`

Access mode: **OAuth** (end users connect their own accounts).

Schema: `teams`, `team_members` (owner/member), `tasks`
(`todo`/`doing`/`done`). A `private.is_team_member()` security-definer helper
avoids recursive policies. `public.create_team()` creates a team and its owner
membership atomically.

Seed: Alice and Bob each own a private team and share **Launch Crew**.

MCP capabilities:

| Tool          | Kind     | Contract                                                          |
| ------------- | -------- | ----------------------------------------------------------------- |
| `list_teams`  | read     | Teams the user belongs to, with their role                        |
| `list_tasks`  | read     | Bounded keyset-paginated collection, optional team/status filters |
| `create_task` | mutation | Insert into a team the user belongs to; returns a compact receipt |
| `update_task` | mutation | Change title/status of a visible task; returns a compact receipt  |

## 6. Verification contract

A starter is shippable only when all of the following pass in CI:

1. **Catalog** – `starter.json` is valid and `chumbo create` copies the kit
   with the documented exclusions (`test/create.test.ts`).
2. **Drift** – regenerating the MCP function with the current package
   reproduces the committed generated files byte-for-byte.
3. **Function** – `deno check` passes against the locally built package, and
   the generated contract test passes.
4. **Web** – the frontend type-checks and builds.
5. **Isolation** (local Supabase) – against the migrated and seeded stack,
   Alice and Bob receive their own and shared tasks only; a create into a team
   the caller is not a member of is refused by RLS; an update to an invisible
   task changes nothing.
6. **End-to-end OAuth** (local Supabase + browser) – an MCP client registers
   dynamically, follows the OAuth challenge to the web app's consent page,
   signs in, approves, exchanges the code with PKCE, and calls the MCP
   function over HTTP. Alice's and Bob's tokens each receive only their own
   and shared tasks, and a task an agent creates appears in the other member's
   web view. The function is served by Deno against the packed runtime, so
   unreleased Chumbo changes are what get tested.

Steps 1–4 run in `pnpm test:starters`. Steps 5–6 run in
`pnpm test:starters:integration`, which expects Docker and the Supabase CLI.

## 7. Distribution

- `npx chumbo create` (this spec).
- Submission to `supabase-community/supabase-samples`, which feeds
  `supabase bootstrap`, after the kit has been exercised by real builders.
- A GitHub template repository mirrored from `starters/<id>` at release time.

## 8. Non-goals and follow-ons

Not in this release: a Next.js variant, an MCP Apps starter, team invitations,
billing, styling frameworks, deployment pipelines, or hosting configuration
beyond a documented SPA rewrite. Each later starter must reuse the same thin
frontend contract (§3.2) and pass the same verification contract (§6).
